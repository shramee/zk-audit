## Scorer and key changes

Both found by checking the automatic outcomes. Separate commits, with a test for the
scorer.

1. **Tie-break (scorer).** A dependency record that lists `sig.go` only as a related
   location (the gnark advisory record) outranked the record on `sig.go:38` itself,
   because the best record of an item was chosen by verdict class only. P10 then read
   the advisory's verdict and severity. Now, within an accepted tier, the record whose
   own location is on the item wins; the stronger verdict breaks the rest. Effect:
   deep P10 severity is read from the real record (low, ok) instead of the advisory
   (medium); the 2026-10-27 baseline re-scores to the same recall with P10 now read
   from its `needs_validation` record.
2. **D5 (key).** The decoy matched `curve check|on.?curve|subgroup`, so a correct
   record about `eddsa.Verify` not checking that `Sig.R` is on the curve scored as a
   false positive (standard: confirmed, deep: needs_validation). D5 is signature
   malleability; it now matches `malleab|canonical` only. I checked the claim against
   gnark v0.14.0 source: `eddsa.Verify` asserts `S <= Order` and that
   `Q = [S]G − [h]A` is on the curve, never `R`. With `R = (0,0)` the add returns
   `(0,0)` and the first cofactor `Double` computes `DivUnchecked(0, 0)`, whose only
   constraint is `0·X = 0`. `X = sqrt(-1)` then reaches `(0,-1)` and `(0,1)` after two
   more doublings, and the final asserts pass. The stock solver leaves that wire at 0,
   so the break needs a prover with a modified solver, which constraints do not
   prevent. It is new key item **O4**; `SigCircuit` has no consumer, so the impact is
   conditional. The answer key keeps the real D5 statement.
3. **O5 (key).** Standard and deep both confirmed that `Pool`'s
   `verifyProof(bytes,uint256[7])` does not match the verifier gnark exports
   (`verifyProof(uint256[8],uint256[7])`, no fallback), so every withdrawal against
   the exported verifier reverts. Verified by re-running both Foundry PoCs (below).
   The fixture's placeholder `Verifier.sol` says it has the public surface of the
   generated verifier, which it does not. The standard run scored this as a false
   positive before the fix.
4. **O3 (key)** also accepts the discarded proving key in `cmd/setup` (`_ = pk`), which
   deep reported and quick reported with other words.

With these, false positives are 0 in all three runs. Before the change standard had 2
and deep had 2.

What the check showed:

- **Honest results.** Where the builder could not run a command it said so. The
  standard PoC 1 and PoC 7 builders returned `result: not_run` and "this is only my
  reading of the constraints" after every Bash call was denied. The orchestrator ran
  them and set `demonstrated` only after the output. No record claims a run that did
  not happen.
- **Controls.** All Go PoCs have an attack, an honest control that fails for the
  right reason (a constraint number in the message) and a sanity witness that passes.
  P1's control is "wrong path rejected", which shows the circuit is not vacuous but is
  not the same witness with only the bug removed; the P2 control is closer.
- **Model PoC and evidence.** Standard's EdDSA record has `evidence: ANALYSIS` and
  `poc.result: demonstrated`; the validator prints `warning: ... poc demonstrated but
  evidence is ANALYSIS`. Both are what `poc-templates.md` asks for (T-CONSTRAINT-MODEL:
  evidence stays ANALYSIS). The schema has no value for "model only", so the record
  reads as a contradiction. The scorer's PoC rate (POC and demonstrated) counts it as
  not demonstrated, which is right.
- **Half a PoC.** Deep's P10 record says `POC` and `demonstrated`, but the PoC shows
  the completeness failure only (the header says "COMPLETENESS side only"). The
  record text separates "Completeness (run)" from "Soundness (analysis)", so it is
  honest in prose, not in the evidence field.
- **Orphan and gaps.** Standard keeps `4_poc_test.go` for the demoted P6 lead without
  referencing it. Deep's PoC 7 needs `test/GenVerifier.sol`, produced by `go run
  ./cmd/setup` and renamed by hand; it is not in `pocs/` (standard saved
  `7_GnarkVerifier.sol`). PoC file numbers do not match report finding numbers
  (report #3 is `6_poc_test.go` in standard). The recorded `command` points at a
  worktree that the run removes, so the file cannot be re-run from the record alone.
- **Execution.** In standard the builders' own test runs were refused (`cd X && go
  test ...` and `| tail` are compound commands): 6 refused attempts, then the
  orchestrator ran 9. In deep the builders found `go -C <dir> test` and ran 4 tests
  themselves. `go -C` is the form that passes a simple-command allowlist.

### Three-pass memory (deep)

`memory.json` exists and is valid JSON: `passes_planned: 3`, `passes_run: 2`, 27
fingerprints, every one with `[1]`, and
`stop_reason: "Pass 2 (critic-targeted wave W2 ...) added no new fingerprint; loop

What actually happened: one full hunt (Turns 3–6, 27 hunters), one critic, one
three-unit wave, one final-clean critic. The orchestrator counted the wave as

evidence that later passes add nothing is therefore not evidence about loop mode: it

### Friction

Concrete, with evidence. S = standard, D = deep, Q = quick.

1. **Every run began with a compound command and was refused.** `S=...; cat $S/VERSION;
   ls ...; mkdir ...` → "This Bash command contains multiple operations" (Q, S, D,
   first tool call). The orchestrator retried with simple commands within seconds, then
   found that `cat` and `ls` outside the target directory are refused too ("only
   concatenate files from the allowed working directories") and switched to `Read`.
   Cost: about 5 s and a few tool calls. SKILL.md Turn 1 reads as one parallel step.
2. **Hunters keep trying shell navigation of std source.** 16 (Q), 49 (S), 31 (D)
   hunter `Bash` calls were refused: `cd $(go env GOMODCACHE)/github.com/consensys/
   gnark@v0.14.0/... && grep ...`, `for f in ...; do cat -n $f; done`, pipelines.
   Each hunter then fell back to `Read` / `Grep` and finished. All 79 + 58 + 19
   denials are `Bash`; none stopped a run. The orchestrator's hunter prompt gives the
   std path as `$(go env GOMODCACHE)/...`, a shell expansion, not an absolute path to
   hand to `Read`.
3. **PoC builders blind in standard.** 21 refused `Bash` calls (S) and 12 (D). Standard's
   builders could not run anything, wrote the test, reported `not_run`; the
   orchestrator ran 9 test commands and fixed the one build error itself. The skill's
   command form (`cd <worktree> && ... go test`) is the one the allowlist refuses;
   `go -C <worktree> test` passes. The builders and the orchestrator all found `go -C`
   by trial.
4. **Safeguard refusals killed agents, with no recovery rule.** In standard 3 hunters
   (I3, V-selector, V-hash) ended with `stop_details.category: reasoning_extraction`
   ("Agent terminated early due to an API error ... safeguards flagged this message");
   the orchestrator retried each once ("retrying it with neutral wording") and all three
   retries completed. Separately the EdDSA PoC builder (PoC 6) silently continued on
   `claude-opus-4-8` after a refusal: 30 messages, 1.17 USD, the longest builder
   (309 s). In deep the orchestrator's own turn was stopped by the classifier
   (`category: cyber`, "Your response above was stopped by a safety classifier") while
   it was spawning the same EdDSA PoC builder. It stopped that builder (`TaskStop`,
   status `stopped`), never retried it, and the EdDSA finding ended as
   `needs_validation` at confidence 50 with no PoC, where standard confirmed it.
   Hunters are told to narrate `[Feynman: ...]`, `[Socratic: ...]` and
   `[Inversion: ...]` steps in their output (`shared-rules.md`); `reasoning_extraction`
   fired on 3 of 24 hunters in standard and 0 of 42 in the other two runs, so the cause
   is not established. The "cyber" stop hit while the orchestrator was writing the
   builder's brief ("Claimed forgery for ANY PubKey and ANY Msg ..."); that is the only
   suspect, not an established cause. Nothing in `SKILL.md` or `orchestration.md` says what to do
   when an agent is refused, and the report does not mention that agents were.
5. **Loop mode not run** (above): the most consequential deviation. Deep's report
   `[NEW]` tags are meaningless.
6. **Ledger update by hand costs a minute and 16 KB.** Q: `jq` over the ledger was
   refused ("may only process JSON from files in the allowed working directories"),
   so the orchestrator rewrote the whole 16 KB `coverage-ledger.json` with `Write`

   asked for.
7. **Saving agent outputs.** `orchestration.md` has the orchestrator save each
   hunter's return. In quick it did, one `Write` per hunter (15 of 19 top-level
   `Write`s). In standard and deep it changed the hunter prompt to "also write your exact
   final return to `<out>/agents/<ID>.md`" (a deviation; 39 and 38 sub-agent `Write`s,
   all under `out/`), then saved the ones that failed itself (V-state in S, I3 in D) and
   saved deep's G3 only after the critic flagged it missing. The same hunter prompts
   hand over the std path as `$(go env GOMODCACHE)/github.com/consensys/gnark@v0.14.0`,
   which hunters pasted into the shell commands that were refused (friction 2).
   `P0` and `W1` appear in the report's `Agents` row as if they were agents.
8. **Critic-to-wave selection undocumented.** Standard's wave covered 2 of the critic's
   7 units; the other five (the `Debug` field, `testCircuit`, the missing `P0.md`, the
   V-hash line numbers, the `Extra` slice's public side) were not run or recorded as

9. **Gate 4 gave different outcomes for one fact pattern.** The owner gate is

11. **Quick's `--no-poc` still ran 5 refuters.** Correct per the skill (the refuter
